# Навантажувальний тест

Інструмент: k6. Сценарій: `loadtest/scenario.js`.

## Команда

```
k6 run -e BASE_URL=http://<alb-dns-name> -e VUS=60 loadtest/scenario.js
```

## Сценарій

Одна ітерація віртуального користувача: 1 × `POST /scooters/` і 9 читань (6 × `GET /scooters/report`, 3 × `GET /scooters/`), потім пауза 0.5 с.

| Фаза | Тривалість | Користувачів |
|---|---|---|
| Ramp-up | 3 хв | 0 -> N |
| Steady | 5 хв | N |
| Ramp-down | 2 хв | N -> 0 |

N = 40. Підбір: пробний прогін 60 VU лише на `/scooters/report` дав ~100 запитів/с при p95 1.1 с на одному інстансі (0.25 vCPU), тобто це його межа. Сценарій із N = 40 генерує ~60-75 запитів/с змішаного навантаження: цього достатньо, щоб CPU одного інстансу вийшов на 100 % і спрацював скейлінг, але без помилок.

Генератор: k6 v0.54.0, запускався з хмарної Linux-машини (затримка мережі до eu-north-1 ~120 мс, вона входить у виміряну латентність).

Ramp-up потрібен, щоб не оцінювати систему в момент холодного старту і дати автоскейлінгу час відреагувати. Різкий старт дав би піки помилок, які не відображають реальну пропускну здатність.

## Результати

Обидва прогони 19.11.2026, N = 40, max_tasks = 3, ліміт 0 % помилок (`http_req_failed < 1 %`) виконано.

Повернення до мінімуму: після прогону 1 - о 23:06:55 (1 інстанс), після прогону 2 - о 23:47:47 (1 інстанс).

Зв'язок RPS, користувачів і затримки (закон Літтла): одночасних запитів ≈ RPS × час відповіді. Кожен VU робить 10 запитів + 0.5 с паузи, тому при 40 VU і ~0.4 с на запит отримуємо ~40 / (10 × 0.4 + 0.5) × 10 ≈ 90 запитів/с як стелю; реальні 62-74 запити/с означають, що сервер, а не генератор, обмежує пропускну здатність - відповіді сповільнюються, і RPS не росте разом з VU.

## Чому p95/p99, а не середнє

Середнє ховає "хвіст": якщо 5 % запитів тривають 3 с, середнє майже не зміниться, а кожен двадцятий користувач страждає. Percentile показує, що відчуває найгірша частина користувачів.
